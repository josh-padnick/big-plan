# Open-PR hygiene before the launch tag

The launch tag must be cut from a tree with no ambiguous in-flight work. Ambiguity here is not untidiness: a branch nobody has ruled on looks the same as a branch someone is still working on, so the question "is everything in?" cannot be answered at tag time without re-deriving it from scratch.

This file answers it once. Every open pull request and every remote branch not merged into `main` carries exactly one disposition:

| Disposition              | Meaning                                                                                   |
| ------------------------ | ----------------------------------------------------------------------------------------- |
| **LANDED**               | The work is on `main`. The branch is residue and has been deleted.                        |
| **SUPERSEDED / CLOSED**  | The work will not land in this form. The reason is recorded per row.                      |
| **DEFERRED-PAST-LAUNCH** | Real work that is deliberately not in the launch tag, named with the issue it belongs to. |
| **LIVE**                 | Expected to land before the tag. Do not close or delete.                                  |

## How a disposition is proved

Big Plan squash-merges, so a merged branch's tip is never an ancestor of `main` and `git branch --merged` cannot answer this question. Every LANDED claim below rests on one of these instead, and none rests on the branch name or on assumption:

1. The pull request is **merged** and its squash commit is present on `main`, matched on the commit **subject line** ending in `(#N)`. Matching the whole message gives false positives, because a reconciliation commit's body cites the pull requests it reconciles.
2. For a stacked pull request that merged into its base rather than into `main`, the change itself is read out of `main`.
3. The branch tip is reachable from `main`.

A branch whose tip is **newer than its own squash commit** is treated as suspect, not as landed, because a commit pushed after the merge landed in nothing. Two such cases were found; both are recorded below rather than deleted.

### Restoring a deleted branch

A deleted branch is not lost. GitHub keeps the objects, so any row above comes back from its recorded tip:

```sh
git push origin <tip>:refs/heads/<branch>
```

GitHub also offers **Restore branch** on the pull request page of every branch that had one.

## Not in scope

The `no-mistakes` remote is a **local** bare mirror (`~/.no-mistakes/repos/…`), not GitHub. Its branches are pipeline staging state, they are not part of the repository the tag is cut from, and they are deliberately untouched.
