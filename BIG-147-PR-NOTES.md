# BIG-147 pull-request notes

The connection-truth use-case matrix this task's acceptance criteria ask the pull-request description to carry, verified against the code on this branch.
The narrative belongs in the pull-request body; the doctrine behind the matrix is not restated here, because each fact already has one owner:

- The Session Reliability boundary rule - attachment and narration are two questions one signal cannot answer, the recovery horizon that bounds held work's explanation, and the answer-time ownership fence - lives in [docs/subsystems.md](docs/subsystems.md).
- Reader-facing behaviour lives in [docs/src/content/docs/reference/reviewing.md](docs/src/content/docs/reference/reviewing.md), under "Connect the coding agent", and the model badge's rule in [docs/src/content/docs/reference/cli.md](docs/src/content/docs/reference/cli.md).
- The rationale sits with the code it constrains: `src/review/shared/agent-timing.ts` for `AGENT_STALL_MS`, `AGENT_RECOVERY_HORIZON_MS` and its multiplier, `src/review/shared/agent-status.ts` for `heldWorkQuiet` and what held work may and may not speak for, and `src/review/browser/agent-connection.browser.tsx` for the recovery section's visibility gate and takeover-aware copy.

## Connection-truth matrix

| Case                                           | What the reviewer sees now                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Agent mid-long-turn, no protocol traffic    | Activity card reads **Agent may be stalled** with the quiet duration; chrome reads **Agent not responding** in the warning tone, not danger red. The thread reads **No progress for Nm** and its cards keep the picked-up treatment rather than flipping to the queue treatment on every quiet stretch. The connection card reads **No recent agent signal**. The recovery section is on screen but warns that the agent may still be working and that connecting a session takes the work over. The answer is accepted when it lands.                                                                                                                                                                                                                                          |
| 2. A second tab open                           | Unchanged. Both tabs read the same server-owned agent snapshot and connection log, so they render the same reading; opening or closing a tab never writes presence, which only the agent's own heartbeat does.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 3. Review-server restart / runtime unreachable | The Agent tab reads **Agent status unavailable** and the recovery section is hidden, because the connector command would target a dead endpoint. The runtime-offline reading tells the reviewer to restart `big-plan review` and open the new URL it prints. Losing only the agent's presence never hides the section - that is the pair that pins this gate.                                                                                                                                                                                                                                                                                                                                                                                                                   |
| 4. Agent process killed mid-turn               | Identical to case 1 for the first 30 minutes, and deliberately so: neither a slow agent nor a stopped one produces a signal, so claiming a disconnection would be the same unfounded assertion this bug is about. The claim being abandoned never makes a later session report a connection. Past the recovery horizon the pickup stops explaining the quiet: the activity card falls through to the ordinary presence answer, the thread reads **No longer reporting**, drops its promise to resolve itself, leaves the working group and offers **Show setup instructions →**, its pill reads **No longer reporting — connect an agent**, new messages read **Blocked - no agent connected**, and the recovery section returns to its plain **Reconnect your agent** wording. |
| 5. Claim lapse and re-claim (connection log)   | The runtime still records a presence edge whenever the heartbeat ages out, because presence genuinely stopped. The log narrates it as a quiet period rather than as a disconnect and a reconnect: rows read **No signal**, durations read **Quiet for _N_** and **Signal returned after _N_ quiet**, the summary counts quiet periods and resumptions, and the stored reason reads **No agent signal within 75 seconds**.                                                                                                                                                                                                                                                                                                                                                       |
| 6. Network blip                                | Unchanged, and deliberately so. Verified by reading `agentProjectionForReviewPoll` and the poll loop rather than by driving a browser: the status clock only advances when a poll returns and is frozen at `lastObservableAtMs` while the runtime is unavailable, so a failed poll never ages the presence lease behind it, and the first poll that succeeds reads the agent's real heartbeat.                                                                                                                                                                                                                                                                                                                                                                                  |
| 7. Browser tab sleep/wake                      | Unchanged, by the same mechanism and the same verification as case 6. No poll runs while the tab sleeps, so no clock advances behind one, and the first poll on wake reads current presence rather than a lease aged across the sleep.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| 8. A second message sent during a quiet turn   | Reads **Queued, _N_ ahead** rather than **Blocked - no agent connected**, because held work explains the silence and the question is a queue position, not a connection verdict. Once the holding claim passes the recovery horizon it reads blocked again, because nothing is left to queue behind.                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| 9. Two claims, one abandoned and one working   | The activity card describes the most recent pickup, not the oldest claim. Before this, a dead R1 and a quietly working R2 made the card report R1's request id, R1's much longer quiet duration, and a thread link to R1 while R2 was the turn actually in flight.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| 10. Agent killed while idle                    | The waiting connection loop checks its spawner on every iteration and once more before claiming, so it ends when the coding agent that started it does. It reports that end in the heartbeat, and the card reads **Agent session ended** within seconds rather than waiting out the aging window; the log's stored reason reads **The agent session ended** rather than **No agent signal within 75 seconds**. A kill that takes the loop down with the agent leaves nothing to report the end, so that case stays on the unchanged 75-second aging path. A request sent after the death is never claimed by the dead session, so it reads **Blocked - no agent connected** rather than **Agent working** (BIG-156).                                                            |
