# Review Storage Decisions

This excerpt captures the weighty choices for persisting plan-review threads and delivering rendered artifacts.
Each decision carries enough tradeoff context to be judged on its own.

## Persistence layer

<BigDecision question="Which persistence layer should back review comments?" status="open">

Comments need durable identities, ordered replies, and range anchors that survive a renderer restart.
The first release runs locally, but the data model should not block concurrent reviewers later.

<Option title="PostgreSQL" recommended summary="Use the relational store the team already operates for durable review state.">

<Pro>
Transactions keep comment threads and their selected-text anchors consistent.
</Pro>

<Pro>
Existing backup, migration, and observability tooling covers the service from its first deployment.
</Pro>

<Con>
Local development requires a database process instead of a single executable and plan file.
</Con>

The repository layer will own the SQL boundary so local preview work does not leak database concepts into the renderer.
The initial schema needs only plans, threads, comments, and immutable selection anchors; presence and notification state remain out of scope.

</Option>

<Option title="SQLite" summary="Keep review state in one embedded database beside the local server.">

<Pro>
The zero-service setup matches the local-first installation story.
</Pro>

<Con>
The single-writer model adds a known migration point before shared review can scale.
</Con>

</Option>

<Option title="Append-only JSON log" summary="Persist each review event as a line in a workspace-owned file.">

<Pro>
Every state transition stays inspectable with ordinary filesystem tools.
</Pro>

<Con>
Compaction, corruption recovery, and concurrent writes become application responsibilities.
</Con>

</Option>

</BigDecision>

## Artifact delivery

<BigDecision question="Where should rendered plan artifacts live by default?" status="decided">

The output should be easy to find after a CLI render and remain explicit when automation needs a different destination.

<Option title="Alongside the source plan" chosen recommended summary="Write the HTML next to the MDX input unless the author supplies an output path.">

<Pro>
The artifact is discoverable from the plan without a cache-inspection command.
</Pro>

<Con>
Generated HTML can appear inside a source-controlled workspace.
</Con>

</Option>

<Option title="Tool-owned cache directory" summary="Collect every rendered artifact under Big Plan's local cache.">

<Pro>
Rendering never adds generated files to the author's project tree.
</Pro>

<Con>
Artifacts become harder to discover and can outlive the source version that produced them.
</Con>

</Option>

</BigDecision>

## Reviewer reminders

<BigDecision question="How should reviewers receive decision reminders?" status="deferred">

Notifications depend on reviewer identity and a live session model that this static delivery does not yet own.
The alternatives remain recorded so the live-review plan can resume from an explicit boundary.

<Option title="Wait for signed-in reviewer identities" recommended summary="Defer reminders until a live review session can route them to a known person.">

<Pro>
Delivery preferences and read state attach to a stable reviewer rather than a browser tab.
</Pro>

<Con>
The static viewer offers no proactive reminder in the meantime.
</Con>

</Option>

<Option title="Browser notifications">

<Pro>
The browser can alert a local reviewer without adding an email provider.
</Pro>

<Con>
Permission prompts arrive before Big Plan can explain which events are worth interrupting for.
</Con>

</Option>

</BigDecision>
