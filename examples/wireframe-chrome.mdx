# Review chrome: marks, controls, and layered surfaces

Big Plan's own review surface is full of chrome a wireframe used to have to fake, and this document draws all of it with the vocabulary that exists for it.

Copy marks on a snippet, a settings gear and an actions launcher in the toolbar, a quick-search palette centered over the page, and a confirmation that covers the page it is about to change: each one is authored rather than approximated, so a reviewer argues about the product instead of about the drawing.

## The reviewer's toolbar

The toolbar carries the plan's identity on the left and the controls on the right, which is the split every real application uses.

A `TopBar` reads that way on its own: the title leads, and every loose control trails.
Nothing in this bar is grouped, because a `Group` written first inside a `TopBar` means something else - it draws ahead of the title, which is where a phone puts its back control and where a desktop bar wants nothing.

The panel rows further down need that split spelled out.
A `Row` gives a flexible share only to a pane - a `Panel`, `Stack`, `Row`, or `Center` - so a mark, a line of copy, and a button keep their natural width and cluster at the start of it, and `justify="between"` would only spread all three evenly.
Wrapping each side in a `Group` makes the row exactly two items, and `justify="between"` then sends those two to the two ends: the command and its copy control, then the lock and its comment action.

The marks are named rather than typed.
A gear is `icon="settings"`, and `iconOnly` keeps the words as the control's accessible name and tooltip instead of drawing them.

Only the search control opens a surface here.
The launcher and the gear are drawn because the toolbar carries them, and a control this prototype does not walk is more honest than a second route into a surface that is not what the control names.

## What each screen settles

The palette and the confirmation are the same element carrying two different settings, and each setting answers its own question.

`backdrop` answers whether the page is still available: the palette leaves it `clear` because nothing about the page became unusable, and the confirmation dims it because the reader has to answer before anything else can happen.
`kind` answers what the surface is: the palette is an ordinary `dialog`, and the confirmation is an `alert`, which is what guards a removal that does not come back.

The page underneath is the same page on all three screens - the same toolbar, the same sections, the same panel - so the only thing that changes when a surface opens is the surface.

Both surfaces center over the page, which is what an overlay draws and what a quick search and a confirmation both do in a real product.
A menu hanging under one toolbar button is a different shape, so this document draws the launcher as the control it is rather than borrowing a centered surface to stand in for it.

Drawing either as an ordinary panel in the column would have hidden both answers behind an arrangement neither surface actually has.
