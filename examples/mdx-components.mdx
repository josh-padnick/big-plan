# Edge Cache Revalidation Plan

This plan moves catalog-page cache revalidation out of request handlers and into a small background queue.
Today an expired entry makes the first reader wait for an origin fetch, so traffic spikes amplify latency precisely when the cache should protect the service.
The proposed stale-while-revalidate path keeps reads fast, bounds origin concurrency, and preserves the current cache key contract.

<Callout type="note" title="Review decision">

Approve the queue boundary, the 90-second stale window, and the rollout gates before implementation begins.

</Callout>

## Goals and constraints

The change targets the 14 catalog routes that share `readThroughCache`.
It does not alter pricing caches or the CDN configuration.

- Serve a stale value immediately while one refresh is in flight.
- Keep origin traffic below 40 requests per second per region.
- Preserve the existing five-minute hard expiry as the final safety bound.
- Emit enough state to distinguish fresh hits, stale hits, and origin fallbacks.

<Callout type="tip">

Use the existing `catalog-cache` worker pool rather than adding a new deployment.
It already has regional concurrency controls and the required service account.

</Callout>

## Request path

The handler will return fresh entries unchanged.
For an entry between 60 and 150 seconds old, it returns the cached value and enqueues one deduplicated refresh; after 150 seconds it falls back to the current synchronous origin read.

| Entry age | Response | Refresh behavior | Budget |
| --- | --- | --- | ---: |
| 0-60 seconds | cached value | none | under 10 ms |
| 61-150 seconds | stale value | enqueue deduplicated job | under 15 ms |
| over 150 seconds | origin value | synchronous fetch | under 800 ms |

<Callout type="warning" title="Deploy ordering">

Create the queue before enabling stale reads, and verify the worker can consume a synthetic refresh job:

```sh
admin-cli cache refresh --key catalog:demo --dry-run
```

</Callout>

The primary implementation change is intentionally narrow and retains the synchronous fallback.

## Worker contract

Each job carries only the cache key and enqueue timestamp.
The worker resolves current catalog data, writes it with the existing TTL, and acknowledges the job only after the cache write succeeds.
The refresh routine itself already exists, so the plan reuses it unchanged.
The worker pool keeps its small, unchanged shape; no files move in or out of it.

```ts
export const refreshCatalog = async (key: string): Promise<void> => {
  const current = await catalogOrigin.read(key);
  await cache.put(key, current, { ttlSeconds: 300 });
  metrics.increment("catalog_cache.refresh_success");
};
```

## Rollout and validation

The rollout uses three cohorts and advances only after a full peak-traffic window.

1. Enable internal catalog routes for 24 hours.
2. Expand to 10% of public traffic for 48 hours.
3. Increase to 100% after the stale-hit ratio and origin request rate remain within budget.

Success requires p95 catalog latency below 120 ms, fewer than 40 origin requests per second per region, and no increase in five-minute hard-expiry fallbacks.
Rollback disables `catalog-stale-revalidate`; the queue and worker can remain deployed because producers stop immediately.
