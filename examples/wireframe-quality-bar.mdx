# Fresh-agent wireframe quality proof

CLEAR keeps the complete design standard memorable. The product sketches use only public Wireframe guidance and defaults.

## CLEAR is the front door

**CLEAR groups the standard; it does not compress it.** Ask the five questions in order, then follow every relevant rule beneath that letter.

- **C · Clear job.** Did decision complexity select the right composition before placement began?
- **L · Layout follows attention.** Does the task itself—not a convenient container pattern—dominate?
- **E · Explicit change.** Does deliberate action visibly unlock selection and continuation?
- **A · Audience language.** Do identity, terms, consequences, and next actions sound natural to this person?
- **R · Real device.** Is this the native interaction pattern for this device and task complexity?

**LOOP** is only the render-and-review workflow. **CRAP** remains the separate standard for the plan page around the artboard.

## C · Clear job

**Pattern before placement**

- Match interaction complexity to decision complexity. Two to five simple alternatives use one dominant `ChoiceGroup` of large `ChoiceCard`s; record comparison may use list/detail; dense operations may use a workspace.
- Never turn a small tablet choice into a miniature list-and-inspector workspace.
- A choice detail must add genuine reassurance or consequence that cannot fit inside the selected card; keep it beneath the choice, not in a second column.
- Let the heading ask once. Put reversibility or reassurance in the subtitle instead of repeating the instruction in a panel title or helper.

**Flow and ownership**

- Give one screen one job and one step one decision. Split choosing, telling, checking, handing off, authenticating, reviewing, approving, and completing when each asks a different question.
- Make the title name the present task—not the next step, a system state, or another actor's future work.
- Make every action and control label describe its immediate outcome. When nearby context already makes that outcome obvious, keep the next action short: `Continue` or `Next: tell us about it`.
- In a sequence, provide one nearby route back and one prominent route forward. A branch may instead offer parallel alternatives.
- Close a learning loop concretely: lead with achievement, answer the original question, show specific evidence, say what remains true in the real world, then offer a purposeful next action.
- Use one achievement headline; a completion badge is metadata, not a second headline. When a concept changes over time, reinforce memory with one compact visual sequence before reassurance.

**Workspace and review surfaces**

- Make every persistent pane earn its width with a distinct, always-useful job.
- Give a collection and preview different jobs: the list supports rapid comparison; the preview supports rapid judgment with urgency, context, recommendation, and a route into the work.
- Keep core inspector properties visible and collapse Related, Activity, and Customer detail. In create/edit flows, keep facts primary, routing together, duplicates conditional, drafts safe during review/cancel, and required validation inline.
- Give every opened form, figure, thread, dialog, drawer, and temporary mode a visible Cancel, Close, Escape, or return path.
- Give each review action one owner: whole-screen comments belong to the screen or slide; element comments belong to selected elements in expanded mode. Never duplicate whole-figure commenting as a floating action.
- State whether visual variations configure one component or represent different components. One concept gets one named owner.

**Reject:** small choices drawn as list/detail; repeated instructions; unearned detail panes; mixed jobs; future-facing titles; actions that exit instead of advance; duplicate routes; redundant panes; doubled completion headlines; receipt-like endings; inescapable temporary surfaces; duplicate comment routes; ambiguous component ownership; list/preview pairs that repeat the same facts.

**Mechanics:** compilation blocks multiple page headers and multiple filled work actions. Wording still requires review.

## L · Layout follows attention

**Order and relationships**

- Create one focal point with deliberate size, position, spacing, and contrast.
- Make visual hierarchy follow decision hierarchy: question or primary work first, supporting facts second, next action last. Celebrate achievement before quieter reassurance.
- Make the primary workspace surface visibly dominant in width, breathing room, and contrast.
- Give the screen an effortless reading order; a focused flow must not require desktop-style left-right-back scanning.
- Use proximity to explain relationships. Put a changed outcome beside the selection that changes it.
- Group by user concepts, not available data. Prefer hierarchy over a wall of containers.
- Nest dependent controls directly beneath their parent in one shared group.

**Emphasis and expression**

- Keep parallel options parallel in grammar, weight, information depth, and target treatment.
- Make each decision option name a distinct title, then place a rule before its criteria. Criteria are smaller than the name; labels are bold with `:`, values regular.
- Keep matrix labels readable at their longest value. Widen or break out the comparison, abbreviate with a nearby legend, or choose another explicit composition before allowing one-word-per-line headers. Center collapsed actions on both axes.
- Separate a one-sentence definition from answer rows with breathing room and one consistent dashed-underline definition affordance.
- Spend the strongest border, fill, badge, type, and color only on the most important content or action.
- Give facts, recommendations with provenance, and side effects at the final action visibly different treatments.

**Simple touch decisions**

- Make the tablet decision itself the focal surface: one centered column of complete option cards, never a left list competing with a right inspector.
- Make the whole option look touchable with border or fill, comfortable padding, hand-drawn icon, title, one-line consequence, and a clear state target.
- Use the iPad canvas through larger type, taller cards, grouped spacing, and decisive contrast; never shrink a desktop form and float it in the frame.
- Quiet graph paper behind the interactive region with a light surface so the grid never competes with the words.

**Anchors and operational surfaces**

- Align comment input, cards, and outcome chips with their source in a quiet side gutter. The highlight carries context, so cards do not repeat selected text or block paths; long bodies collapse behind `… more`.
- Give the Comments panel a top border and one scannable staged → submitted → resolved lifecycle instead of an undifferentiated gutter pile.
- Keep highlights outside glyphs. Use padding, background, underline, or an outside marker so comment presence is obvious without obscuring text.
- Let toolbars own viewer actions. Keep note submission, live counts, zoom, Fit, and maximize in stable positions; keep the tray header distinct and its primary action inside its footer—never detached over the canvas.

**Scan and expression**

- Make lists scan in stable rows—title/time, person/organization, state/identifier—and give customer, agent, and internal messages consistent distinct treatments. Unread, priority, assignment, waiting, selection, and open state cannot share one signal.
- Use one sticky inbox toolbar for search, filter count, and sort, with active chips beneath. Show the result count once, keep create secondary during triage, and add bulk controls only for real batching.
- Size controls to their values: channels 320–400px, times 140–180px, and readable forms around 760px.
- Optimize for a five-second scan before careful reading.
- Use decoration only to identify content, communicate state, reinforce the emotional goal, or explain an unfinished visual decision.

**Reject:** a tablet decision split into columns; thin-row pseudo-selection; graph paper louder than the task; a shrunken desktop form floating in an iPad; equal-weight or squeezed panes; card walls; floating metadata or actions; cramped matrix headers; criteria styled like option titles; definitions that read as answers; comment borders crossing text; repeated anchored context; detached tray actions; unrelated dependencies; recommendation/value ambiguity; oversized empty panels; biased choices; decorative filler; anything louder than its importance.

**Mechanics:** plain panels, dominant derived panes, and `Rail` encode the default hierarchy. Compilation blocks equal desktop thirds and four-or-more outlined siblings; geometry tests block cramped panes, overlap, and dead bands.

## E · Explicit change

**State and flow**

- Make a selected row, card, or mode agree visibly with its dependent outcome.
- Reveal information progressively: choices before summary, review before approval, and no later-stage detail before the present decision.
- Paint hover, focus, active, selected, disabled, error, done, current, and unavailable states unmistakably.
- Make progress communicate state: completed steps look complete, exactly one step is current, future steps are quiet, and task labels never repeat generated numbers or checkmarks.
- Show causal results next to the action that produces them.
- Give actor and mode changes a visible boundary: a new screen, actor-specific heading, simplified content, lock cue, and different treatment.
- Treat authentication as identity proof, never consent: handoff → authenticate → review → approve or decline. `Unlock to review` cannot buy or approve.
- Preserve the first actor's exit before handoff; once authentication starts, the next actor may enter a focused gate.

**Deliberate choice**

- Never preselect a consequential choice. The initial decision screen starts unselected; a deliberate tap reveals the selected state and only then reveals or enables continuation.
- Give every unselected choice its own selected-state destination. The destination selects the same title and consequence; polished options may never collapse into one generic outcome.
- Make selected touch state unmistakable with several signals together: filled radio, stronger border, changed background, and checkmark or an equally explicit mark. Tint or a thin left line is insufficient.

**Risk and persistence**

- Make dangerous mode switches change several signals together: selection, surface and border, heading or icon, placeholder, action, and persistent visibility warning.
- Give every piece of state one owner; duplicate controls must be explicitly synchronized shortcuts.
- Keep recommendations labeled with their evidence until accepted or changed.
- Before a setting changes, show its scope, outcome, current state, and dependency.
- Make persistence observable: Saving → Saved, undo after consequential auto-save, unsaved counts for explicit save, and no silent navigation loss.

**Comments and mode lifecycle**

- Make comment presence obvious at its exact anchor in inline and expanded modes. A gutter marker selects that same anchor and enters the same flow as text selection.
- Any nonempty selection—including a whole paragraph—shows one compact icon-plus-`Comment` affordance, not a formatting toolbar. It disappears when selection or hover ends; passive scrolling never leaves orphaned buttons or sprays controls across the page.
- Show the full lifecycle: staged comments navigate to targets; responded threads collapse to one-line outcome chips, expand in place, use their reply box as per-comment chat, and keep plan-wide chat separate.
- Keep edit and remove easy to find on the author's own comment; confirm immediately before removal.

**Safety and continuity**

- Keep counts live and labels unconfusable after create, edit, delete, submit, and response. Persist only an exact signal such as `Needs your answer 2`, never stale or ambiguous `Comments 2`.
- Confirm destructive actions. Deleting authored content in an edit review stays visible as a struck-through diff; it never disappears silently.
- Use idiomatic focus paint: border shift plus soft halo, not a thick double ring. On mode exit, return focus to a sensible container or prior control.
- Preserve document scroll, selected target, active screen, and relevant internal scroll across maximize, drawer, and comment-mode changes.
- Render controls only with a valid state and anchor. No unexplained dot, empty pill, footer hover line, or delayed-hide workaround on load.
- Distinguish selection from opening: background plus outside indicator selects; unread and priority use different signals; Enter or a labeled preview route opens.
- Show required-field errors beside fields before submit. Name the person, address, and event for notification consent; never enable it silently. Preserve a draft or warn on Cancel.
- Settings show visible `On`/`Off` text as well as position and contrast. Keep dependencies visible-but-disabled under parents, show `Connected` or `Connect Slack`, and offer a safe test action.

**Reject:** preselected consequential choices; premature continuation; generic summaries after specific choices; faint or single-signal selection; premature summaries; ambiguous progress; single-signal dangerous modes; duplicate state owners; invisible comment anchors; comment clutter; highlights that cover text; stale counts; ambiguous alerts; unconfirmed deletion; silent destructive edits; awkward or stranded focus; lost scroll or selection; invalid load-state controls; unlabeled recommendations; silent persistence; scope-free settings; heading-only handoffs; mixed audiences; Face ID or PIN labeled as approval.

**Mechanics:** compilation requires one selected record beside visible detail, checks navigation targets and Stepper state, and rejects authored progress numbering. State primitives own interaction paint; viewer primitives own comment lifecycle, focus return, and context preservation.

## A · Audience language

**Implementation principles**

- Use concrete words, outcomes, amounts, and time from the audience's mental model: `$27.50 to go`, `two Friday payments left`, or `Nothing will be bought yet`.
- Use one term per concept and one label per destination.
- Preserve the user's words after selection: `Ask about a purchase` becomes `You chose: Ask about a purchase`, never `Purchase request` before a request exists.
- Prefer natural copy: `See how much money I would have left` beats `See what money stays in my wallet`.
- Keep identity and escape visible in a quiet tablet header—`Eddy's Wallet` and `Back to my wallet`—so the child is never trapped.
- Make one screen speak to one audience; change mode and heading before addressing the next actor.
- Name the current branch—a purchase request, loan question, or confusing topic—not a generic summary.
- Make reassurance name the actual risk and what remains unchanged: `Unlocking does not approve or buy anything`; `This was practice—no money moved`.

**Review-surface language**

- Let the anchor carry comment context. Use the slide or screen title for a thread title and keep the highlighted source visible; never repeat a paragraph excerpt or internal block path in the card.
- Separate person from organization, or present one identity that names both. A side effect such as email consent names the person, destination, and triggering event.
- Group settings by event or goal, not technology. Keep daily/digest wording consistent, name delivery time and timezone, and say who integration-dependent behavior reaches.
- Name toggles and alerts by their current live outcome: `Show comments`, `Hide comments`, or `Needs your answer 2`. Update label and count together; a panel toggle must not look like an ordinary action.
- Keep definitions to one plain sentence behind the same dashed-underline affordance everywhere.
- Avoid internal, technical, adult-oriented, or agent-process language the audience would not say.
- Serve the emotional goal—capable, safe, motivated, informed, or in control—without hiding facts.
- Prefer specific feedback and a visual recap over praise the product cannot verify.

**Operational language**

- Keep saved views—reusable queues such as `All`, `Mine`, and `Unassigned`—separate from temporary filters such as `Waiting ×`, `SLA risk ×`, and `+ Add filter`.
- Prefer time-to-act over arithmetic: `First response due in 4m`, `Breached by 6m`, or `Waiting 2h`; never require elapsed/target calculation or color alone.

**Reject:** terminology drift after selection; naming an unsubmitted choice a request; unnatural outcome copy; a trapped flow without identity or escape; abstract labels where plain language exists; mixed audiences; branchless summaries; repeated comment excerpts or block paths; stale or ambiguous count labels; ordinary-action styling for state toggles; inconsistent definition treatments; saved-view/filter ambiguity; elapsed/target arithmetic; generic reassurance; technical badges; unverified praise.

**Mechanics:** lint keeps agent-process copy outside the artboard. Audience fit, terminology, and risk wording require review.

## R · Real device

**Cross-device contracts**

- Use a native layout language, not one design scaled three ways: dense B2B patterns on desktop, iPadOS composition on tablet, and iOS push navigation on phone.
- Put hand-drawn irregularity in strokes, grid, icons, and rough borders—never alignment, spacing, reading order, contrast, information architecture, or target size.
- Keep three legible type roles: page title, content, and metadata.
- Make controls unmistakable through shape and state. Tablet and phone targets are at least 44px.
- In an expanded multi-screen viewer, show screen names as a vertical list on the left; arrow keys move through it and keep the active screen visible.
- Enter expanded mode fit-to-viewport and centered on both axes; allow zoom below 100%. Comment and selection markers keep a fixed readable screen size under zoom instead of scaling with the canvas.
- Reserve element comments for expanded mode: select the element, then comment. Inline mode keeps one calm whole-screen comment area and passive scrolling never triggers element affordances.
- Keep the expanded toolbar stable: `Add N notes to plan feedback` stays flush left in inline and expanded modes and never overlaps the live note count.

**Desktop passes:** a 1200 × 820 application viewport with no app-wide horizontal scroll; flexible minmax-style columns keep a 64–180px navigation rail, 280–320px list, dominant primary surface, and 280–320px inspector in one row; persistent panes scroll independently while the header and composer remain anchored; narrower widths collapse navigation, then inspector, before overflow; tight vertical rhythm; Linear-style settings; create/edit as a route or true modal; and keyboard shortcuts for list movement, search, open, compose, mode switch, send, assign, and resolve that supplement visible controls.

**Desktop rejects:** equal thirds; whole-page scrolling while answering; app-wide horizontal scroll; four squeezed screens; a sidebar taking a third; floating tablet navigation; two large settings cards; inflated chrome; oversized iPad sheets.

**Tablet passes:** fixed 1020 × 720 landscape or 820 × 1180 portrait iPad frame, about 1.44:1, laid out to fit with no internal scroll; no browser bar; quiet identity/escape header; touch-first type and 44px controls; wider gutters; and composition chosen by task complexity. Two to five simple choices use one dominant centered `ChoiceGroup` of tall `ChoiceCard`s, start unselected, and reveal explicit continuation only after tap. Master/detail is reserved for a real collection whose persistent detail adds useful context. A light interaction surface quiets the grid instead of shrinking content.

**Tablet rejects:** a simple decision as list/detail or `Rail`; preselection; faint row selection; a stretched near-square bezel; compressed desktop density; browser chrome; squeezed desktop sidebars; tiny text; desktop task flows.

**Phone passes:** 390 × 720 minimum; compact top bar; one column; 44px controls and 52–64px rows; bottom destinations; fewer fields; progressive disclosure; list → detail push navigation.

**Phone rejects:** desktop shells; side-by-side properties; a vertical iPad; height-only tablet cards; desktop copy squeezed narrow.

**Mechanics:** device presets own widths, fixed tablet ratio, shell availability, type roles, flexible pane widths, independent overflow, anchored conversation chrome, touch floors, contrast, and state paint. `ChoiceGroup` and `ChoiceCard` own simple-decision dominance, touch surfaces, and multi-signal selection; compilation blocks initial preselection, premature continuation, nonmatching option outcomes, and competing tablet columns. Viewer primitives own fit, centered expansion, below-100% zoom, fixed-size markers, expanded navigation, toolbar placement, focus return, and scroll preservation. Browser geometry checks fence app-wide overflow, primary dominance, independent panes, anchored header/composer, 1.39–1.44 tablet ratio, shells, readable panes, overlap, unjustified dead bands, and target sizes.

## What the curation absorbed

**Every prior standard remains explicit under one owner.**

**Foundational and flow rounds**

- **Fourteen hierarchy principles → CLEAR.** Focal point, reading order, proximity, grouping, scanning, restrained decoration, emotional goal, and rough fidelity live under Layout, Audience, and Real device.
- **Original task-flow round → CLEAR.** One job, goal-matching actions, selection outcomes, progressive reveal, hierarchy over containers, attention order, unmistakable affordances, mode boundaries, concrete language, and importance-based contrast remain explicit above.
- **Task-flow refinement round → CLEAR.** All 23 principles remain explicit: the eight check-step rules, seven audience/authentication/handoff rules, and eight learning-loop rules—including one completion headline, a compact memory recap, concrete real-world state, and purposeful return.
- **Maximize navigation and commenting-calm round → CLEAR.** Expanded screen list and arrow navigation live under Real device; select-then-comment and passive-scroll calm live under Explicit change; whole-screen versus element ownership lives under Clear job; context and scroll preservation live under Explicit change.

**Component and workspace rounds**

- **Commenting rounds 4–5 → CLEAR.** Anchor-visible presence, glyph-safe highlights, context-free side cards, `… more`, edit/delete with confirmation, one shared anchor flow, complete lifecycle, outcome chips, per-comment versus plan chat, live exact counts, unconfusable labels, and adversarial lifecycle review remain explicit.
- **Decision rounds 4–5 → CLEAR.** Option-name rules, smaller bold-colon criteria labels with regular values, readable matrix headers, centered collapsed actions, idiomatic focus, exit paths, separated one-sentence dashed-underlined definitions, and explicit component ownership remain explicit.
- **Diagram rounds 5–6 → CLEAR.** Valid load state, visible deletion diffs, anchor markers, distinct tray chrome with contained footer, toolbar-owned actions, no redundant whole-diagram button, no meaningless footer hover, fixed-size zoom markers, stable flush-left note action, and safe focus return remain explicit.
- **Desktop workspace round → CLEAR.** Verified complete: viewport fit; flexible bounded columns; independent pane scrolling; anchored header/composer; primary dominance; multi-signal modes; one state owner; scannable lists; speaker differentiation; observable auto-save; progressive inspector; keyboard support; compare-versus-judge panes; saved views versus filters; time-to-act; sticky toolbar; selection/open clarity; side-effect confirmation; customer identity; duplicate evidence/actions; recommendation provenance; grouped routing; specific consent; validation/draft safety; explicit setting scope/effect/dependency/state; nested controls; outcome labels; visible On/Off; persistent save; consistent dependencies/sizing; integration readiness; and no horizontal overflow.
- **CLEAR gold-gap critique → CLEAR.** All twelve corrections remain explicit: composition follows decision complexity; touch surfaces look touchable; selection uses several signals; consequential choices start unselected; child vocabulary survives selection; details earn their place; instructions are not repeated; identity and escape stay visible; tablet space enlarges rather than shrinks; the grid quiets behind interaction; copy sounds natural; and next actions stay short. The governing tablet rule is now primitive-owned: the decision dominates, never a miniature workspace.

**Prior standards and mechanics**

- **STAMP → retired, detail retained.** Space, Tiers, Align, and Minimal boxes live under Layout and mechanics; Plain state lives under Explicit change.
- **Per-device principles → Real device.** Desktop, tablet, and phone each retain distinct pass criteria and anti-patterns.
- **Type, aspect, state, and target rules → mechanics beneath CLEAR.** Primitives, compile diagnostics, and browser geometry checks own the facts.
- **LOOP and CRAP → separate jobs.** LOOP proves a render; CRAP structures the surrounding plan page.
