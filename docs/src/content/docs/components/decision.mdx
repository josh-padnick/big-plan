**Purpose: ask the reviewer one question and end with their confirmed answer.**

`Decision` presents one tradeoff as a comparison matrix: options are columns, criteria are rows, and a single rationale panel beneath explains whichever option the reader is looking at.
Comparison comes first and explanation second, and selecting an option swaps the panel without moving anything on the page.
Escalate to [ComplexDecision](/components/complex-decision/) when the call needs weighted scoring or a reversibility record, and drop to [SimpleDecisionSet](/components/simple-decision-set/) for quick calls.

## Authoring

```mdx
<Decision question="How does the skill reach the end user's agent?">

Context the reviewer needs before the options.

<Option title="Embedded in the CLI" recommended summary="A skill command prints the file verbatim.">

<Consideration title="Version fidelity" verdict="Exact" tone="good">

The skill is compiled into the package, so it can never disagree with the installed CLI.

</Consideration>

<Consideration title="Works offline" verdict="Yes" tone="good" />

Optional prose detail, shown with the considerations in the rationale panel.

</Option>

<Option title="Docs-site download" summary="Setup fetches the skill from the docs site.">

<Consideration title="Version fidelity" verdict="Drifts" tone="bad" />

<Consideration title="Works offline" verdict="No" tone="bad" />

</Option>

</Decision>
```

## The contract

- `question` is required; `status` is `open`, `decided`, or `deferred` (default `open`).
- At least two `Option` children, at most one marked `recommended`.
- Every `Option` needs at least one `Consideration` with a required `title` and `verdict`; `tone` is `good`, `bad`, `mixed`, or `neutral` (default `neutral`).
- Every `Option` must list the same `Consideration` titles in the same order, so the options stay comparable.
- A `verdict` is at most 24 characters: it is a value to compare, not a sentence to read. Keep one scale per row.
- `status="decided"` requires exactly one `Option` marked `chosen`, and a `chosen` Option requires `status="decided"`.
- Consideration and option bodies are markdown without headings, footnotes, or typed components.

Each violation fails `validate` and `render` with a positional diagnostic.
Run `big-plan guidance Decision` for judgment-level usage guidance.

## What the reader gets

The matrix answers "how do these differ" in one look, before the reader has read a sentence of reasoning.
Each verdict carries a word, a glyph, and a colour, so no reader depends on hue alone.
Below it, one rationale panel explains the option currently in view - the recommended one until the reader chooses otherwise.
Every panel occupies the same grid cell, so the region is as tall as the longest rationale and **choosing never moves the page**.

An open decision renders as a native radio group, so picking an option, moving between columns with the arrow keys, and the selected column header all work with scripts disabled; without scripts every rationale panel simply stays stacked and readable.
The whole column header is the click target, and selecting highlights the entire column.
Recommendation, selection, and outcome stay three separate states: a recommendation is a neutral chip, a picked column takes the accent, and a settled one takes the decided colour.
An open decision never announces that it is open - being asked is what makes it open.

Every open decision also offers a quiet **Propose another approach** link that reveals a text box only when asked, so a reviewer is never limited to the options the agent thought of.
The confirm row sits directly beneath the rationale panel and names the current choice beside the action.
Confirming drops the columns the reader turned down and records the answer in the rendered document.
Delivering that answer back to the agent arrives with review commenting; until then, tell the agent your answer in conversation.

Below the reading breakpoint the matrix scrolls sideways, and a hint says so to the readers who need it.
